## Qué se inicializa antes del bind (lectura de código)

Orden real en `main.rs` (los números son de este árbol, no de un run):

1. `apply_onnx_thread_cap(None)` y `engine_device = config.inference.device` (`main.rs:724-725`).
2. Se lanzan **tres cargas ONNX en paralelo** con `spawn_blocking` (T-DSH-55):
   - sparse BGE-M3 (`main.rs:728`),
   - dense mxbai (`main.rs:749`),
   - reranker Jina (`main.rs:766`).
3. Se **esperan** las tres, en orden, con `await_engine_load(handle).await` (`main.rs:780`, `:890`, `:946`). Esa función solo hace `handle.await` (`embeddings.rs:886-894`): **no hay timeout, ni cancelación, ni fallback por tiempo**.
4. Solo después se hace `tokio::spawn(start_http_server_with_download(...))` (`main.rs` line 1420-1422).

Conclusión directa: **cualquier bloqueo indefinido en una de las tres cargas deja el kernel sin puerto**. No es el repo map (D-39b ya lo movió a background después del bind) ni el bind en sí.

### Dónde se elige el proveedor

- `InferenceDevice` por defecto = `auto_select_device()` (`config.rs:832`).
- En Windows, `auto_select_device()` devuelve **DirectML sin probar si DirectML funciona** (`config.rs:912-924`); solo mira `cfg!(target_os = "windows")`.
- `build_execution_providers(Directml)` construye `DirectMLExecutionProvider::default().build()` (`embeddings.rs` line 1389-1394) y se lo pasa a `TextInitOptions` / `SparseInitOptions` / `RerankInitOptions`.
- Las tres inicializaciones (`TextEmbedding::try_new` `embeddings.rs` line 934; `SparseTextEmbedding::try_new` line 1315; `TextRerank::try_new` line 1462) pueden bloquear dentro de ONNX/DirectML antes de devolver `Ok`/`Err`.

### Dato que no encaja y hay que tratar con cuidado

DSH midió el primer `/health` a 24,5 s en su run final, pero el código actual spawnea HTTP después de las tres esperas. Eso sugiere que en ese run concreto las tres cargas ya habían terminado (o que el timeline del informe mezcla runs); **no invalida** el orden del código. Para D-43 lo relevante es: si una carga con `auto` se cuelga, el spawn HTTP no llega a ejecutarse.

## Hipótesis ordenadas (de más probable a menos)

### H1 — Contención/mutua exclusión al crear 3 sesiones DirectML a la vez (T-DSH-55)

T-DSH-55 pasó de cargas en serie a tres `spawn_blocking` simultáneos. Con `device=cpu` eso es seguro; con `auto` en Windows las tres piden el mismo `DirectMLExecutionProvider`/dispositivo DML. La inicialización de DirectML puede serializarse o bloquearse esperando al dispositivo mientras las otras dos también están dentro. `device=cpu` no toca DML y por eso es determinista.

**Cómo falsearla (DSH, kernel `test-run-*`):**
1. `device="auto"`, `[silva] hybrid_sparse_enabled=false`, `reranker_enabled=false` → solo dense. Medir tiempo hasta `/health`.
2. Repetir con dense+sparse (reranker off) y dense+reranker (sparse off).
3. Comparar con las tres activas.
   - Si **una sola** carga auto se cuelga → no es contención; pasar a H2/H3.
   - Si una sola bindea y **la combinación** se cuelga → H1 confirmada.
   - Repetir con `device="cpu"` para descartar que el problema sea el modelo/carga.

### H2 — DirectML bloquea bajo carga de CPU/GPU (no por concurrencia)

`auto` elige DML aunque la GPU esté ocupada por otro proceso (entrenamiento, navegador, otro agente). La creación/compilación de la sesión DML puede esperar al driver sin límite. DSH ya vio que la máquina estaba al ~100% de CPU en sus runs; el run frío con `auto` llegó a 142 s y otro no bindeó en >20 min.

**Cómo falsearla:**
1. Mismo `device="auto"` en una máquina **idle** (sin cargo/otros agentes) y medir; si bindea en un tiempo razonable, la carga es el factor.
2. Repetir bajo carga controlada (un `cargo build` o un benchmark) y comparar.
3. Medir CPU/GPU y estado de hilos del proceso durante el cuelgue (`Get-Process`, Process Explorer, `procdump` si hace falta):
   - CPU ~0 y threads esperando → bloqueo en driver/DML.
   - CPU al 100% → cómputo/lenta, no deadlock.

### H3 — DirectML mal instalado o incompatible (DLL/proveedor), y el error se convierte en espera

`onnx_runtime_ort_compatible()` (`embeddings.rs:712`) solo valida que `onnxruntime.dll` sea cargable y la versión; **no valida `DirectML.dll` ni el proveedor DML**. `build_execution_providers` tampoco hace probing. Si el EP no está o la GPU no soporta el modelo, `try_new` puede fallar tarde o quedarse esperando.

**Cómo falsearla:**
1. Inspeccionar el directorio del `onnxruntime.dll` en uso: presencia/versión de `DirectML.dll` y `onnxruntime_providers_shared.dll`.
2. Arrancar `test-run-*` con `RUST_LOG=ort=debug,tylluan_kernel=info` y ver hasta qué log llega cada engine (`Loading ... engine`, `Inference device: DirectML`, `engine ready`).
3. Probar `ORT_DYLIB_PATH` apuntando a una ORT **CPU-only** conocida: si `device="auto"` entonces bindea o falla rápido, el problema es el proveedor DML/DLL, no el modelo.
4. Probar `device="directml"` explícito (debe reproducir `auto`) y `device="cpu"` (control).

### H4 — Saturación del pool de blocking / thread pool de ONNX

`apply_onnx_thread_cap(None)` y las tres cargas comparten el pool de `spawn_blocking` y los hilos internos de ONNX. Si el thread cap o la carga del sistema dejan sin hilos, las esperas pueden alargarse; menos probable que H1-H3 porque solo son tres tareas y el bind es async.

**Cómo falsearla:**
1. `inference.max_threads = 1` vs default en el mismo `test-run-*`; comparar.
2. Contar hilos del proceso durante la carga y ver si el pool está agotado.
3. Repetir con una sola carga (H1) para separar “pool” de “DML”.

## Propuesta (sin cambiar nada todavía)

1. **Instrumentación barata primero:** log `info!` antes y después de cada `await_engine_load` con `engine`, `device` y `elapsed_ms`; y un `warn!` si supera N segundos (sin abortar). Hoy el log “engine ready” existe, pero no hay un “waiting for X since …” que diga cuál de las tres se colgó.
2. **Probe de DirectML al arrancar:** si `device=auto` en Windows, comprobar que el EP DML se puede crear antes de meterlo en las tres sesiones; si no, caer a CPU con un `warn!` único. Esto evita que un DML roto secuestre el arranque.
3. **Bounded wait:** `tokio::time::timeout` alrededor de cada `await_engine_load` (p. ej. 120-180 s, decisión de José) y degradar a BM25/RRF como ya hace un `Err`. No reduce el timeout de guilds; es el arranque.
4. **Alternativa estructural:** mover el `tokio::spawn(start_http_server...)` **antes** de las esperas de modelos (dejando `/health` en `starting`), para que el puerto abra aunque una carga se cuelgue. D-39b ya abrió HTTP antes del repo map; esto extiende la misma idea a los modelos. Implica que recall puede degradar hasta que terminen las cargas.
5. **Si H1 se confirma:** serializar las cargas cuando `device != Cpu`, o cargar primero dense y lanzar sparse/reranker después del bind. Mantener el paralelismo solo para CPU.

## Decisión que necesita José

- **¿Qué debe hacer `device = "auto"` en Windows?**
  - (A) Seguir eligiendo DirectML, pero con probe + timeout + fallback a CPU (mantiene el rendimiento cuando DML funciona).
  - (B) Cambiar el default de Windows a **CPU** hasta que DML sea fiable (arranque determinista, menos rendimiento).
  - (C) Mantener `auto` y mover el bind HTTP antes de las cargas (el puerto abre, pero el recall tarda en estar listo).
- **¿Timeout de arranque?** Valor concreto (120/180 s) y si al agotarlo se cae a CPU/BM25 o se reintenta en background.
- **¿Serializar cargas con GPU?** Aceptar el coste de arranque (antes era en serie) a cambio de eliminar la contención de tres EPs DML.

No cambié el default ni ningún timeout (fuera de alcance de D-43). DSH es quien puede ejecutar los `test-run-*`; yo no arranco kernels.
