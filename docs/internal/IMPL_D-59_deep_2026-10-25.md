# IMPL D-59 — el handler MCP exige `Content-Type: application/json`

**Agente:** Deep (OpenCode)
**Fecha:** 2026-10-25
**Base del patch:** `origin/main cb41c03`.
**Patch:** `E:\tylluan-patches\deep\D-59.patch` (3 798 B).
**Estado:** implementado y verificado en worktree. **NO verificado por HTTP real. NO comiteado** (lo comitea el TL).

---

## Problema

`mcp_handler` (`transport/http/api_v1/mcp.rs`) leía el cuerpo y hacía `serde_json::from_slice` sin mirar `Content-Type`. Por eso `POST /messages` con `text/plain` (petición CORS "simple", sin preflight) ejecutaba `tools/list`/`tools/call`. T-DSH-85 lo confirmó con el router en proceso.

## Cambio

- Nuevo `reject_non_json_content_type(method, headers)`:
  - Solo actúa en `POST`; `GET`/`OPTIONS` no cambian.
  - Acepta `application/json` con parámetros (`; charset=utf-8`), comparación case-insensitive.
  - Cualquier otro valor, o ausencia de cabecera → **415 Unsupported Media Type** con `{"error":"Content-Type must be application/json"}`.
- El handler llama a la puerta **después de OPTIONS y antes de `to_bytes`/parse**: un `text/plain` no llega a construir el JSON-RPC ni a `tools/call`.
- No se toca `auth.rs` ni `transport/http/mod.rs` (son de DSH/T-DSH-86).

## Auditoría de clientes

Antes de cambiar se revisaron los POST a `/messages`, `/mcp` y `/api/v1/mcp`:

| Cliente | Content-Type | Estado |
|---|---|---|
| `scripts/ci/claims/write_gate_rejects.sh` | `curl -H "Content-Type: application/json"` | OK |
| `scripts/stress_test.py` | `aiohttp` con `json=payload` | OK (aiohttp lo pone) |
| Tests de integración que usan `/mcp` (`blackboard_e2e`, `approve_*`, `asi06_*`, `pipeline_tests`, `sovereign_e2e`, etc.) | `CONTENT_TYPE: application/json` o `.json(...)` | OK; un barrido automático no encontró ninguno sin cabecera |
| Docs (`CLIENT_INTEGRATION_GUIDE`, `ADDING_A_GUILD`) | ejemplos `curl` con `Content-Type: application/json` | OK |
| `guilds/core/llama_backend.py` | `/v1/messages` es el endpoint Anthropic del proveedor, **no** el MCP del kernel | fuera de alcance |
| Dashboard | usa `/api/v1/mcp/external` (REST), no JSON-RPC MCP | no afectado |

No apareció ningún cliente real que dependiera de enviar `text/plain` al MCP del kernel.

## Tests

Cuatro tests nuevos en `mcp.rs`:

| Test | Qué fija |
|---|---|
| `text_plain_is_rejected_with_415` | `POST` + `text/plain` → 415. |
| `missing_content_type_is_rejected_with_415` | Sin cabecera → 415. |
| `application_json_with_charset_is_accepted` | `application/json; charset=utf-8` → no rechazo. |
| `get_and_options_are_not_gated` | GET/OPTIONS conservan su comportamiento. |

El rechazo ocurre antes de `to_bytes`, así que el tool no puede ejecutarse. Los tests existentes de MCP con JSON siguen cubriendo el camino 200.

## Impact

- **Superficie:** `transport/http/api_v1/mcp.rs`, solo POST del handler MCP. Sin cambios de auth, CORS, rutas ni SSE.
- **Seguridad:** `text/plain` deja de ser una vía CORS simple para ejecutar tools; el cuerpo ni se parsea. `application/json` (con charset) sigue funcionando; clientes legítimos no cambian.
- **Compatibilidad:** cualquier cliente que enviara JSON sin `Content-Type` o con `text/plain` ahora recibe 415; no se encontró ninguno en el repo.
- **No depredación:** D-59 estaba asignado a Deep; no se tocó el checkout compartido.
