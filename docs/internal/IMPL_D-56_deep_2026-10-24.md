## Problema (seguimiento de D-52)

`federation_approve_peer` ya devolvía 500 si `update_ed25519_pubkey` fallaba, pero el peer ya tenía `approved=1`. Un peer aprobado sin pubkey hace que `ingest_from_peer` se salte `verify_envelope` (fail-open).

## Cambio

- `PeerDb::set_approved(name, bool)` (`federation/mod.rs`): actualiza solo `approved`, conservando auth token, secreto, pubkey y demás columnas.
- `persist_peer_pubkey_or_revert()` (`api_federation.rs`):
  - Si la pubkey se persiste → `Ok(())`.
  - Si falla → intenta `set_approved(false)` y devuelve el error original + el resultado de la reversión (`approval reverted`, `approval NOT reverted: peer not found`, o el error SQLite).
- El handler usa ese helper. En error:
  - `tracing::error!` con el motivo.
  - `reload_peers_cache` para que el estado en memoria refleje `approved=false`.
  - Responde **500** con `status` `approval_reverted` o `approval_revert_failed`, `name` y `error`.
- Si la reversión también falla, el peer podría seguir aprobado; el error lo dice explícitamente y no se oculta.

## Test

`failed_pubkey_update_reverts_approval`:

1. `PeerDb` real en tempdir, peer insertado con `approved=true`.
2. `ALTER TABLE federation_peers DROP COLUMN ed25519_pubkey` desde otra conexión: la pubkey falla, `approved` sigue existiendo.
3. `persist_peer_pubkey_or_revert` devuelve `Err` que contiene `approval reverted`.
4. Consulta directa `SELECT approved` → **0**, no queda aprobado sin pubkey.

## NO verificado

- No ejecuté el flujo real de aprobación con un peer que devuelva `/identity` y falle la escritura; el test fuerza el fallo de columna.
- No probé el caso en que la reversión también falla (solo está el `error` con `approval_revert_failed`); no hay test de esa rama.
- No hice una transacción única; la alternativa elegida es UPDATE + reversión. El peer puede quedar aprobado si la reversión falla, pero el error lo declara.

## Impact

- **Superficie:** `federation_approve_peer` y `PeerDb` (identidad de peers). Sin cambios de esquema ni de `verify_envelope`.
- **Seguridad:** un fallo al guardar la pubkey ya no deja un peer aprobado sin firma verificable; el estado se revierte y la caché se recarga.
- **Comportamiento:** la aprobación puede devolver 500 aunque `update_approved` haya escrito; el peer se desaprueba. El mensaje distingue reversión OK/fallida.
